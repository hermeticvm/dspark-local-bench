# DSpark ecosystem status, October 2026

Checked 2026-10-24 against primary sources. Things move fast; open an issue if something here is out of date.

## llama.cpp

- **DSpark merged** in [#25173](https://github.com/ggml-org/llama.cpp/pull/25173) on 2026-07-28 as
  `--spec-type draft-dspark`. It's built on the DFlash drafter path. The PR reports a 1.88× decode speedup
  for Qwen3-8B bf16 on CUDA in SPEED-Bench (1.21× over DFlash).
- **Extended to other backbones and models:** Gemma4 (#29226), LFM2 (#27383), Nemotron 3.5 (#27804),
  bailingmoe3 (#27508), Nanbeige (#27730), DeepSeek-V4 MTP + DSpark (#25784), speculators-format
  checkpoints (#26275). The spec type is now detected automatically from the draft GGUF's metadata (#26814).
- **The confidence head is a static cutoff only:** `--spec-draft-p-min P` truncates each drafted block at
  the first position whose predicted confidence is below `P`. The default, 0, means off. There's no
  load-aware scheduler and no adaptive draft length for DSpark.
  `docs/speculative.md` calls this flag `--spec-draft-conf-min`, but `arg.cpp` defines `--spec-draft-p-min`.
- **Adaptive draft length** exists only for MTP, in open PRs:
  [#27210](https://github.com/ggml-org/llama.cpp/pull/27210) (`draft-mtp-adaptive`, very active) and #25726.
- **"Greedy decoding is lossless" holds for quality, not bit for bit.** #25173 states the output is identical
  to plain greedy decoding. Measured here on b11865 (Vulkan and ROCm), only 5–6 of 16 answers were identical,
  and a classic draft model diverged just as often. Batched verification rounds differently and flips near-tied
  tokens, so this is general to llama.cpp's speculative decoding, not specific to DSpark.
- **Prompt processing slows down when a drafter is loaded.** In a [KDnuggets test](https://kdnuggets.com/speed-up-llm-inference-with-dspark-speculative-decoding)
  (Qwen3-8B Q4_K_M, CUDA) it fell from 295 to 88 t/s, while decode went from 95 to 125 t/s.

## Ollama

[ollama#17016](https://github.com/ollama/ollama/issues/17016) is closed as completed. `DRAFT ./dspark.gguf`
in a Modelfile works, and since 0.40.7 llama-server infers the speculative type on its own. Anything merged
into llama.cpp's speculative code reaches Ollama users.

## Independent work

- [Ankk98/llama.cpp PR #1](https://github.com/Ankk98/llama.cpp/pull/1) is an open draft POC on Gemma-4-12B
  QAT, using Vulkan on a Radeon 8050S iGPU and CUDA on an RTX 3090. It reports 1.4-1.6×, with 4 fixed draft
  tokens working best. **Confidence-scheduled verification made it slower.**
- SGLang and NVIDIA NeMo AutoModel support DSpark on the server side.

## Open questions this repo targets

1. Does any `--spec-draft-p-min` beat 0 at batch size 1, and on which hardware?
2. Does the best draft length depend on task category or backend?
3. How do Vulkan and ROCm compare for verifying draft blocks on AMD consumer GPUs?
4. Is the prompt-processing penalty acceptable for interactive single-user use?
5. Later: can an adaptive controller driven by the confidence head beat the best static setting?
